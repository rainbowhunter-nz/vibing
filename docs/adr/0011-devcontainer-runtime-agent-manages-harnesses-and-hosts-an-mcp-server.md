# The Devcontainer Runtime Agent manages coding harnesses and hosts an MCP server for delegation

The agent was scoped (ADR-0004, ADR-0008) as the owner of a single Agent Session: receive `start_agent_session` from the Control Plane, run `claude -p`, emit events. In practice the higher-value workflow is different: a human drives a **main harness** (Claude Code) *directly inside* the Devcontainer and wants to delegate sub-tasks to *other* coding harnesses (Codex, Cursor). Having the main harness shell out to those CLIs non-interactively is unreliable; the goal is a dependable, structured way to spawn them, plus relief from the real pain of authenticating each harness inside every ephemeral container.

We **re-scope the Devcontainer Runtime Agent** to keep its existing Agent Session lifecycle untouched and add three harness-management responsibilities, all operating on *managed harnesses* (Codex, Cursor; extensible) — never on the main harness, which authenticates itself and acts only as a *client*: (1) **check** whether a managed harness is installed and authenticated; (2) **install + authenticate** it from credentials the Control Plane delivers (see ADR-0012); (3) **host an MCP server** the main harness calls to start Delegated Runs (see ADR-0013). The two models **coexist**: the top-down Control-Plane-driven Agent Session and the inside-out main-harness-driven delegation are independent paths into the same agent process. Replacing the session model was rejected — it is already built, works, and costs nothing to keep while the delegation workflow proves itself.

The MCP server is **runtime-owned and served over streamable HTTP at a stable localhost URL** inside the container, not a stdio program the harness spawns. The runtime agent is already a long-running process; hosting the server there gives it a lifecycle decoupled from the main harness (it stays up across main-harness restarts, serves concurrent Delegated Runs, and shares the same install/auth state the agent already tracks). stdio was rejected because its lifecycle is tied to the client and it would run as a separate process from the agent, forcing install/auth state to be shared across a process boundary for no gain. The URL is **stable and documented; the user adds it to their harness config once** — auto-writing into the main harness's config was considered (lower friction) but rejected for MVP as too magic and harness-specific. The server binds `127.0.0.1` with no MCP-level auth: it is a single-user tool inside an isolated container.

The tool surface is `list_harnesses` (install/auth status, so the main harness can decide what to delegate to) and `spawn(harness, model, prompt, detached?, cwd?)` plus `get_status`/`get_result`/`stop` for detached runs. `model` is a free-form passthrough each harness validates. Each managed harness is fronted by a **per-harness adapter** — the single place that knows that harness's install command, credential location/format, auth check, and non-interactive invocation. The adapter is the core extensibility seam: adding a harness is adding an adapter.

This extends the container contract from ADR-0004. Harness binaries no longer need pre-installing (the runtime installs on demand, ADR-0012), but the container must provide a package manager and network egress (egress was already assumed for the Anthropic API), and the runtime now binds a localhost MCP port.

Consequences: the agent process now does two unrelated jobs (session lifecycle + harness management), and a new transport (HTTP MCP) lives alongside the existing Control-Plane WebSocket client in one asyncio process. The protocol grows: an `authenticate_harness` Command, harness-status events, and Delegated Run events (ADR-0012, ADR-0013). The stable-URL-added-once choice leaves a one-time manual setup step we may later automate.

Status: accepted
